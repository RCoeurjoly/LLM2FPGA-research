# LLM2FPGA Systems Engineering View

This file is a reusable scaffold for reasoning about LLM inference on FPGA at a system level.
It is intentionally practical: what parts of the stack are controlled in hardware, software, and methodology.

To reduce speculation, this map is evidence-scoped:
- *S* = captured from the survey registry only.
- *P* = verified directly from a downloaded PDF.
- *U* = unknown / unverified.

Current entries are marked as provisional (*S*) until the paper is deeply read and upgraded.

* 1) End-to-end inference stack

1. **Model semantics contract**
   - Input artifact: PyTorch model and target behavior (equivalence target).
   - Required: same user-visible output behavior (or bounded approximation) for the same input.
   - Core transforms: quantization, pruning, operator decomposition.

2. **Compilation and scheduling layer**
   - Graph lowering: PyTorch/ONNX/MLIR/Tensor DSL → compiler IR.
   - Mapping decisions: dataflow, kernel tiling, pipelining, parallelism topology.
   - Control decisions: prefill schedule, decode schedule, batching policy.

3. **Hardware architecture layer**
   - Compute engines: matmul/attention/MLP kernels, lookup-based paths, overlay fabric.
   - Memory system: on-chip SRAM/BRAM/URAM/regs plus off-chip DDR/HBM.
   - Fabric interfaces: AXI, host command channel, DMA.
   - Reconfiguration paths: static bitstreams or DPR partitions.

4. **Runtime layer**
   - Host/board orchestration: weights load, KV state management, stream setup.
   - Performance policy: latency-vs-throughput scheduling, batching, clock/power adaptation.
   - Error handling and restart strategy.

5. **Validation and systems QA**
   - Golden comparison against reference inference.
   - Layer-level and end-to-end accuracy checks (top-k output, perplexity, tokens/sec, latency).
   - Timing + resource closure + power checks.

* 2) Decision axes for this repo

When comparing papers, use these axes in a fixed order:

- **Functional equivalence**: Can it reproduce CPU/PyTorch behavior?
- **Model expressiveness**: Which op classes are supported?
- **Model size support**: What parameter/sequence-size envelope is feasible?
- **Compute efficiency**: Throughput/latency improvements and bottleneck behavior.
- **Memory system realism**: Is off-chip bandwidth / host transfer modeled honestly?
- **Toolchain openness**: Does implementation depend on proprietary synthesis/placement?
- **Portability**: Can flow move across FPGA families/boards?
- **Reproducibility**: Are code, settings, and versions accessible and runnable?

* 4) Scoring rubric (first pass)

Use a 1–3 score per axis (1=weak, 3=strong), with a note and evidence source.

| Axis                  | 1                          | 2                                 | 3                                              |
|-----------------------+----------------------------+-----------------------------------+------------------------------------------------|
| Functional confidence | no clear equivalence path  | partial/clear in selected kernels | explicit equivalence strategy                  |
| Hardware openness     | proprietary stack only     | mixed OSS + proprietary           | OSS-first path                                 |
| Resource portability  | board-specific only        | modest retargeting                | architecture described at reusable granularity |
| Scalability model     | single fixed configuration | fixed family + tuning knobs       | clearly parameterized design space             |
