# Constraint Programming for LLM Inference on FPGA

#+TITLE: CP for LLM Inference on FPGA (LLM2FPGA DSE)
#+DATE: 2026-06-10

* Why this file exists

Use this as the working design record for a first practical CP-guided design-space exploration (DSE) flow for LLM inference on FPGA, focused on our open-source flow (yosys / nextpnr / open build tooling) and a fixed board target (Kintex-7 480T class).

The intent is:

- CP acts as a *feasibility and candidate-pruning* engine.
- Fast models/estimators rank candidates.
- Yosys/nextpnr/HIL provide *truth* (resource, timing, performance, correctness).
- Results are fed back into CP as learned constraints and priors.

This intentionally avoids replacing placement/routing with pure CP for whole designs.

* Core scope decision

| Layer | Role of CP | Keep/avoid |
|-------+------------+------------|
| PyTorch operator graph mapping | Use CP constraints | Keep |
| Quantization and tiling choices | Use CP variables | Keep |
| Dataflow / scheduling / memory placement | Use CP constraints | Keep |
| End-to-end RTL correctness pipeline | Use CP + test harness | Keep |
| Full physical place-and-route | Avoid as primary solver | Avoid initially |
| Floorplanning / timing-hint extraction | Use CP on reduced state | Optional later |

Reason: full P&R scales poorly for CP, but floorplanning and timing-hint constraints are tractable with board-specific feedback.

* Problem statement (as an optimization)

- Given:
  - a fixed board/FPGAs + measured memory/clock/bandwidth envelope,
  - one operator graph from a small LLM/LLM-like model,
  - allowed implementation options (quantization, tiling, operator variants, scheduling),
  - resource/timing/correctness constraints,
- choose mappings that maximize useful objective(s) while staying implementable.

Primary practical objective:
- maximize throughput proxy (tokens/s or cycle/token) under constraints.

Secondary objectives:
- maximize timing robustness / synthesis pass probability,
- minimize compile cost,
- minimize resource footprint for near-optimal throughput.

** Hard constraints

1) Resource budgets (conservative estimates)

- LUT(cfg) ≤ LUTmax
- FF(cfg) ≤ FFmax
- DSP(cfg) ≤ DSPmax
- BRAM(cfg) ≤ BRAMmax
- URAM(cfg) ≤ URAMmax
- WNS_pred(cfg) ≥ WNS_min (or timing-pass proxy if available)

2) Functional arithmetic constraints

- hidden_dim % tile_k = 0
- hidden_dim % tile_n = 0
- num_heads % num_heads_par = 0
- acc_bits ≥ ceil(log2(tile_k)) + w_bits + a_bits - 1

3) Memory/ bandwidth constraints

- bytes(weights) + bytes(act_buf) + bytes(kv) + bytes(intermediate) ≤ memory_budget
- DDR_bw_req(cfg) ≤ DDR_bw_meas * safety_margin
- if ext_mem=1 then (weights_in_bram, weights_in_uram) = 0
- if kv_in_bram=1 then kv_size_model ≤ bram_kv_cap

4) Scheduling/latency constraints

- stage_cycles(cfg, op_id) formula-compatible with selected tile sizes
- total_cycles_prefill ≤ prefill_budget
- total_cycles_decode ≤ decode_budget
- II(cfg) ≥ pipeline_ii
- if use_sparse=0 then sparse_group must be 0

5) Compilation/runtime practical constraints

- if use_dsp_mul=0 and use_lut_mul=1 then LUT_budget headroom must hold
- use_dsp_mul + use_lut_mul ∈ {1,2}   ; allow hybrid if supported by codegen
- build_seed_count(cfg) ≤ seed_budget
- max_total_variants in one batch ≤ experiment_budget

6) Correctness constraints (post-build check, not a pre-build inequality)

- CP includes a conservative domain guard:
  - quantization choices must be supported by conversion tool and reference testbench
  - operators requiring unsupported kernel variants are disallowed
- Accuracy/faithfulness validated after synthesis/HIL (see loop below)

** Soft constraints / preferences

Use objective weights or soft penalties for:
- prefer lower compile complexity:
  - penalize very large tile_k/tile_n combinations
- prefer deterministic pipelines:
  - penalize mixed variable-precision per-layer choices unless justified by quality gate
- prefer simple storage layouts:
  - penalize DDR-only placement unless required

* Solver architecture

** Loop topology

1. Parse model + supported operator set
2. Expand candidate variables from model graph + hardware profile
3. Solve CP-MIP feasibility problem under hard constraints
4. Rank top-K feasible configurations by cheap estimator score
5. Run synthesis/P&R for top candidates (multi-seed)
6. Measure:
   - pass/fail, timing, resources, II/Fmax proxy, tokens/s proxy, correctness
7. Store in experiment DB
8. Add learned constraints / update surrogate and rerun

This is a closed-loop search:

- CP gives "likely feasible and useful" candidates
- HIL says if timing/RTL reality contradicts estimator
- Learned rules improve next CP iteration

** Suggested tools

- Model frontend: PyTorch graph capture (`torch` / `torch.ao`), optional torch-mlir
- CP engine: OR-Tools CP-SAT first
- Secondary solver lane: MiniZinc + CP-SAT-compatible formulation for model sanity
- Optional second stage: Z3/optimize for small symbolic checks and boundary debugging
- DB: SQLite or DuckDB for experiment provenance
- Estimator: local python module with analytic surrogates
- Build runners: existing make/flow scripts calling yosys + nextpnr-xilinx
- Reporting: JSONL + parquet + org tables for papers/design notes

* Constraint updates from measured outcomes

When a config consistently fails timing:
- add nogood clauses:
  - tile_k >= threshold ∧ lanes > threshold -> avoid
  - chain_len > N ∧ target_clock > fclk -> require extra pipeline stage
- relax resource-based optimism:
  - replace underestimation factors with measured multipliers for similar region

When hardware fails while estimate passed:
- add minimum margins to II/bandwidth/accumulator constraints
- tighten ext_mem usage for failing memory placement patterns

When a config passes and performs well:
- record as seed set for local neighborhood search
- widen local tile/lane exploration around it

* Risk register

- Resource model mismatch: underestimated BRAM/DSP from RTL variants.
- Timing closure noise: seed-dependent routing can hide feasibility.
- Surrogate error: analytic model may rank wrong near-boundary points.
- Build variance: external tool versions and flags can shift pass/fail boundary.
- Correctness drift: fixed-point saturation and ordering effects across kernels.

Mitigation:
- keep CP constraints conservative,
- keep all post-build checks strict,
- track per-tool versions in DB metadata,
- gate objective progression on correctness + timing passes.

* Success criteria (first 6 weeks)

1. >100 feasible candidates generated by CP without full synthesis
2. At least 10% fewer synthesis attempts needed to reach top candidate than naive grid
3. Reproducible pipeline:
   - same seed list → same top-20 candidates
4. One config that:
   - passes timing in >2/3 seeds,
   - preserves baseline correctness checks,
   - beats current baseline tokens/s at matched resource budget

* Open questions

- Should objective be lexicographic (feasible → perf → robustness → resources)
  or weighted sum?
- Do we optimize on measured tokens/s only, or also estimate on a model-agnostic benchmark?
- Is correctness gate:
  - top-1 agreement OR token-level agreement, or both?
- How aggressive should cross-layer shared quantization be (uniform per model vs per-layer)?
- How strict should timing robustness be in first loop: pass >= 2/3 seeds or single best seed?

* Fast Viability and Kill Switch Protocol

This is the execution rule for avoiding sunk-cost loops. No project work
continues unless it passes each gate below within the stated time budget.

** Objective of each gate

- Detect “definitely not viable” paths early.
- Keep every failure as reusable evidence (for learning and backtracking).
- Preserve velocity by enforcing strict, repeatable exit criteria.

** Gate 0: Feasibility Screening (1 hour)

Input: one paper/pipeline/approach under consideration.

Pass only if all are true:
- Target board token is explicit and maps to our board profile.
- Input model path exists (or can be exported from PyTorch).
- Kernel set is finite and implementable with a concrete front-end path.
- At least one open dependency required for each stage is available this week.

Fail reasons for immediate kill (high confidence):
- No board profile compatibility.
- Closed-only toolchain at any mandatory stage (e.g., required proprietary compiler/placer/SDK).
- Paper claim requires non-reproducible manual setup (single private artifacts with no scripts).

** Gate 1: Toy-Build Viability (1 day)

Input: one operator or one block (quantized linear or depthwise matmul slice).

Actions:
- Generate one candidate from CP model.
- Run full flow end-to-end: graph -> codegen -> yosys/nextpnr -> compile artifacts.
- Execute a single HIL check with a fixed seed and fixed prompt.

Pass only if:
- Synth/route artifacts exist and are reusable.
- No structural functional mismatch on the toy check.
- Measured pass time is finite and repeatable (<= 2x variance on rerun with same seed).

Kill conditions:
- Build never reaches bitstream-ready artifact.
- Reproducibility variance is unbounded (flaky failures > 30% across three reruns).
- Functional mismatch on toy check.

** Gate 2: Scalability Signal (2 days)

Input: TinyStories-1M or equivalent tiny pipeline with same code path.

Actions:
- Run 2–3 model-size increments with same skeleton (e.g., 1M, 2M, 4M equivalent parameterization).
- Keep all hyper-parameters fixed except model scale.

Pass only if:
- Same design path compiles for all three points without new manual edits.
- Throughput and resource usage change as monotonic/understandable curves (no chaos).
- Correctness gate remains stable (same top-1 on a fixed reference set).

Kill conditions:
- One size jump forces invasive manual redesign.
- Non-monotonic behavior indicates brittle sizing assumptions.

** Gate 3: Objective Pressure Test (3 days)

Actions:
- Compare this approach against current baseline on tokens/s and compile-time cost.

Pass only if:
- Better or equal latency/throughput at similar resource bracket.
- Better or equal compile determinism (success rate, retries, wall time).
- Clear path to the next model size step.

Kill conditions:
- No objective headroom after 3 fixed iterations.
- Any advantage only from changing the target model definition instead of architectural gains.

** Decision policy

- If a gate fails: close ticket with a short evidence packet and mark as non-viable:
  - command logs
  - config + board profile hash
  - failure mode code (tool-chain/dependency, functional, performance, compile variance)
- If a gate passes: expand candidate set by one axis only.
- Never open two new axes before both the objective and proof-of-correctness gates are passed.

** Failure-as-evidence template

Use this fixed schema for each rejected path:

- `path_id`: unique id (paper/task/approach)
- `hypothesis`: concise statement of expected gain
- `evidence`:
  - paper claim link
  - commit hash or workflow id
  - logs + artifact paths
- `failure_mode`: one of {toolchain-block, reproducibility-fail, correctness-mismatch, compile-intractable, perf-miss, scale-brittle}
- `measured_metric`: failing quantitative data
- `exit_rationale`: why continuing is not efficient

This turns ambiguous “maybe” work into explicit learning records and keeps you from optimizing in circles.
