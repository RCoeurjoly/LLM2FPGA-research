* Why this matters

The LLM2FPGA moonshot depends on making the design loop concrete enough that a
solver can reason about it:

- model behavior becomes a contract,
- board constraints become finite domains and inequalities,
- build failures become learned constraints,
- experiment records become reusable evidence,
- search quality is judged against naive grid/random and hand-picked baselines.

The main question to carry through these notes:

#+begin_quote
What modelling choices make the CP-SAT problem small, explainable, and useful
enough to guide real FPGA experiments?
#+end_quote

* CP-SAT modelling notes

Use this section for modelling patterns from the CP-SAT primer.

** Modelling principles to extract

- Prefer finite integer domains over unconstrained numeric freedom.
- Make illegal states unrepresentable where possible.
- Separate hard constraints from objective preferences.
- Use auxiliary variables to expose useful structure instead of hiding logic in
  opaque expressions.
- Add redundant constraints when they improve propagation and make infeasibility
  easier to diagnose.
- Keep the first model small enough to debug by inspection.

** LLM2FPGA variable candidates

Semantic variables:

- `operator_scope`: linear, FFN, attention projection.
- `mode`: prefill, decode.
- `w_bits`, `a_bits`, `kv_bits`.
- `accuracy_gate`: exact layer output, bounded error, token agreement.

Architecture variables:

- `tile_m`, `tile_n`, `tile_k`.
- `lanes`.
- `acc_bits`.
- `use_dsp_mul`, `use_lut_mul`.
- `pipeline_ii`.
- `fused_block`.

Memory variables:

- `weights_in_bram`, `weights_in_uram`, `weights_in_ddr`.
- `kv_in_bram`, `kv_in_ddr`.
- `stream_width`.
- `buffer_depth_class`.

Physical-risk variables:

- `target_clock_class`.
- `timing_margin_class`.
- `routing_pressure_class`.
- `seed_budget`.
- `floorplan_region_tag`.

** Hard constraints to model first

- Shape divisibility:
  - `hidden_dim % tile_k = 0`
  - `out_dim % tile_n = 0`
- Arithmetic safety:
  - `acc_bits >= ceil_log2(tile_k) + w_bits + a_bits - 1`
- Resource envelope:
  - estimated LUT/FF/DSP/BRAM/URAM under conservative margins.
- Memory fit:
  - selected on-chip buffers must fit available BRAM/URAM budget.
- Bandwidth:
  - estimated DDR bytes/cycle must stay below measured board envelope.
- Implementation support:
  - unsupported combinations are disallowed up front.

** Objective candidates

Start lexicographic rather than with a fragile weighted sum:

1. feasible under hard constraints,
2. lower estimated cycles per token,
3. higher timing margin,
4. lower compile-risk class,
5. lower resource footprint among near-equal designs.

* Modelling traps

- Encoding too many architecture ideas before the first truth loop exists.
- Treating estimated timing as truth instead of a risk signal.
- Letting the objective hide correctness or buildability constraints.
- Using CP-SAT only as grid-search syntax.
- Adding learned constraints that overfit one failed run.
- Comparing against no baseline, which makes any found candidate look good.

* Implications for the moonshot hypothesis

The moonshot note should stay centered on a small inverse-design loop:

- one board,
- one model/layer shape,
- one operator family first,
- explicit baselines,
- CP-generated candidates,
- real build/correctness feedback,
- learned constraints,
- measured reduction in synthesis attempts.

Project Bodger-style inspiration is useful only if it strengthens this loop.
Otherwise it risks becoming platform-first thinking.
