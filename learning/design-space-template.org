# Design-Space Evaluation Template (Paper-by-Paper)

Use this template to convert each paper from a “name” into an engineering assessment.
Keep entries short and evidence-linked to the survey tables and PDFs.

To prevent speculative summaries, every card in this file starts as provisional and must be
upgraded to verified status when the PDF is read.

- Status: *S* = based on survey table only.
- Status: *P* = verified from PDF text/tables/figures.
- Status: *U* = unknown or ambiguous.

* Common fields

1. Paper ID
2. Problem statement
3. Target workload (e.g., GPT-style LLM, Mamba, generic model)
4. Primary subsystem affected (Model / Compilation / Architecture / Memory / Runtime / DSE)
5. Main optimization tactic
6. Resource assumptions (FPGA class, memory, HBM/DDR, multi-device)
7. Equivalence strategy (how it maps to PyTorch/CPU baseline)
8. Scalability signals (model size, seq length, batch)
9. OSS implementation viability (code + toolchain + reproducibility)
10. Kintex-480T suitability (quick judgement)
11. What to verify next (explicit open question)

** ID 1: TeLLMe (arXiv:2504.16266)
Status: P
- Problem: first FPGA design in this repo to claim full support for both prefill and autoregressive decoding on one edge accelerator.
- Target workload: ternary LLM inference (1.58-bit weights, 8-bit activations), with evaluations including Bitnet W1.58 and LLaMA2-style models.
- Primary subsystem: Architecture + scheduling + memory system.
- Tactic: table-lookup ternary matmul engine, fused prefill/decoding attention with reverse reorder, and quantization/dequantization units.
- Resource assumptions: AMD/Kria KV260 target (Zynq UltraScale+), 7 W power target.
- Equivalence strategy: functional validation appears at accelerator-level comparison, but no full framework for proving PyTorch equivalence is stated.
- Scalability: supports up to 1024-token context and reports prefill latency 0.55–1.15 s and 9.51 tokens/s in KV260 evaluations.
- OSS viability: No (artifact-only status in current registry; no code link confirmed in repo data).
- Kintex-480T: Low.
- Verify: confirm end-to-end parity protocol and whether the extra prefill-optimized logic affects equivalence assumptions.
- Evidence sources: Abstract; Intro & Sec. III (system decomposition); Sec. IV (results, Table IV, Table V).
