# State of the Art: Constraint Programming for LLM Inference on FPGA

#+TITLE: State of the Art: Constraint Programming for LLM Inference on FPGA
#+DATE: 2026-06-11

* Purpose

Sequencing note:

- The current `~/LLM2FPGA/` ad hoc/traditional TinyStories-on-YPCB architecture
  should be finished first.
- This survey informs later CP modelling, not an immediate replacement of the
  active Task 6 implementation path.
- CP should progressively model parts of the measured baseline when a real
  design bottleneck appears.

This survey answers a practical moonshot question:

#+begin_quote
Can OR-Tools / CP-SAT be the architecture and memory-schedule optimizer for
mapping PyTorch/ONNX LLMs onto the YPCB Kintex-7 board with DDR3, while
yosys/nextpnr-xilinx handle physical implementation?
#+end_quote

Detailed design note:

- [[file:../learning/mlir-fabric-cp-mapped-design.org][MLIR Compute Graph + FPGA Resource Graph + CP Mapped Design IR]]

The answer from the current evidence is:

- Yes, CP/CP-SAT is a plausible fit for *architecture-level discrete decisions*:
  quantization, tiling, buffer sizing, memory placement, resource assignment,
  and coarse schedules.
- No, OR-Tools should not be treated as the first detailed FPGA PnR engine.
  Exact placement/routing is a separate physical-design problem with specialized
  representations and tools.
- The likely research gap is not "CP for FPGA" in general. That exists. The
  likely gap is *DDR3-aware inverse architecture scheduling for LLM operators*
  on a small open-toolchain FPGA target, with yosys/nextpnr feedback converted
  into solver constraints.

* Landscape map

** Layer 1: CP for HLS scheduling, binding, and resource assignment

This is the strongest prior-art region.

Classic CP work models high-level synthesis decisions such as:

- operation scheduling,
- resource binding,
- register sharing,
- communication/channel scheduling,
- latency/resource tradeoffs.

Representative references already tracked in this repo:

| Registry ID | Work | Solver family | Transferable idea |
|-------------+------+---------------+-------------------|
| 38 | Constraints-Driven Scheduling and Resource Assignment | CP / JaCoP | finite-domain operation scheduling and resource binding |
| 39 | Global Assignment and Scheduling via HCDG and CP | CP / JaCoP | conditional behavior, binding, sharing constraints |
| 40 | Communication Scheduling on SoPC with CP | CP | channel/event ordering under architecture constraints |
| 41 | Constraint Programming in Embedded Systems Design | CP / MiniZinc | where CP helps in embedded scheduling/mapping |

Relevance to LLM2FPGA:

- high for M0/M1,
- not because these papers solve LLM inference,
- but because they show how to represent scheduling, resource conflicts, and
  communication as finite-domain constraints.

** Layer 2: CP/SAT/SMT for FPGA physical design

There is research on constraint-style physical design:

- SAT formulations for detailed routing,
- CP-style module placement,
- SAT/SMT placement legality for heterogeneous FPGA fabrics,
- ASP/SAT symbolic synthesis loops.

Representative references:

| Registry ID | Work | Solver family | Practical lesson |
|-------------+------+---------------+------------------|
| 43 | SAT-based detailed FPGA routing | SAT | useful for legality/feasibility subproblems, not first full-flow replacement |
| 44 | CP module placement on FPGAs | CP | coarse/static/DPR module placement can be constraint-modeled |
| 45 | SAT-based heterogeneous FPGA placement | SAT/SMT | exact placement is possible in restricted formulations |
| 46 | ASP/SAT symbolic synthesis | ASP/SAT/SMT | synthesis loops can combine generation and validation |

Relevance to LLM2FPGA:

- medium as conceptual prior art,
- low as the first implementation path.

Policy:

#+begin_quote
Do not use OR-Tools as the first detailed PnR engine. Use OR-Tools to produce
architectures, schedules, and coarse physical-risk hints; use yosys and
nextpnr-xilinx as the physical truth layer.
#+end_quote

** Layer 3: DNN / accelerator DSE

Modern accelerator exploration often uses:

- analytical models,
- ILP/MILP,
- CP/CP-SAT,
- heuristics,
- RL,
- LLM-guided search,
- hardware-in-the-loop feedback.

Relevant repo entries:

| Registry ID | Work | Solver/search style | Relevance |
|-------------+------+---------------------+-----------|
| 20 | LLM-Driven DSE of FPGA-based Accelerators | LLM-guided DSE over SECDA/Vivado HLS | useful loop shape, weak YPCB/OSS fit |
| 28 | Autonomous Accelerator Design with SECDA | generated accelerator workflow | useful ambition, blocked by SECDA/Vivado/Zynq assumptions |
| 29 | Holistic Optimization Framework for FPGA Accelerators | HLS optimization framework | useful DSE framing, blocked by Vitis/OpenCL |
| 47 | MATCHA-style CP-SAT DNN deployment mapping | CP-SAT deployment/mapping | useful analogy for mapping decisions |

Relevance to LLM2FPGA:

- high for loop design,
- mixed for implementation,
- most flows depend on proprietary HLS or non-YPCB boards.

** Layer 4: LLM inference on FPGA

Most LLM-on-FPGA papers focus on architectures, quantization, memory systems, or
runtime schedules rather than CP as the central design engine.

Relevant families:

| Family | Examples in registry | What they teach | CP gap |
|--------+----------------------+-----------------|--------|
| quantized matmul / MAC primitives | TeLLMe, XtraMAC, LUT-LLM | low-bit datapaths, table/LUT/DSP tradeoffs | CP could choose primitive per layer/tile |
| memory-aware pipelines | FlightLLM, FlexLLM, Memory Pipeline Disaggregation | memory traffic dominates many LLM stages | CP could schedule DDR/BRAM traffic |
| dataflow / streaming compilers | Spatial acceleration, StreamTensor, HLSTransform | explicit streams, FIFOs, fusion | CP could choose buffer/fusion/schedule variants |
| runtime routing / speculation | MASE, SkipOPU, PD-Swap | dynamic decode/runtime policies | later CP target, not M0 |

State-of-art observation:

#+begin_quote
LLM FPGA literature is rich in hand-designed or compiler-guided architectures,
but there is no clear mature blueprint for OR-Tools-driven, DDR3-aware,
open-toolchain LLM inference mapping on a Kintex-7-class board.
#+end_quote

* Where OR-Tools fits

OR-Tools should sit between model graph analysis and hardware generation.

#+begin_src text
PyTorch / ONNX
  -> graph normalization and shape extraction
  -> OR-Tools architecture/schedule solve
  -> candidate config
  -> RTL/template/CIRCT/HLS-like codegen
  -> yosys synthesis
  -> nextpnr-xilinx route/timing
  -> simulation / HIL measurement
  -> learned constraints back to OR-Tools
#+end_src

** Good OR-Tools variables

Model/operator variables:

- operator family: Linear, FFN, attention projection,
- per-layer or shared quantization,
- supported approximation policy,
- decode vs prefill mode.

Architecture variables:

- tile sizes,
- lane count,
- accumulator width,
- DSP vs LUT implementation,
- pipeline II target,
- stream width,
- fusion/split choices.

Memory variables:

- weights in BRAM vs DDR3,
- activation buffer depth,
- double-buffering,
- DDR3 burst length class,
- prefetch distance,
- reuse factor,
- KV-cache placement later.

Scheduling variables:

- compute stage order,
- DMA/read/write windows,
- buffer ownership,
- overlap between DDR3 fetch and MAC execution,
- host/board phase boundaries.

Feedback variables:

- timing-risk class,
- resource-pressure class,
- previous failure no-goods,
- seed retry budget.

** Bad first OR-Tools targets

- exact LUT/FF placement,
- exact routing resource assignment,
- full nextpnr replacement,
- arbitrary PyTorch graph lowering,
- full TinyStories-1M before the DDR3 Linear monkey is isolated.

* DDR3 and PCIe in the solver

** DDR3

DDR3 is part of the inference hot path.

For OR-Tools, model DDR3 as constrained shared bandwidth plus transaction
structure:

- bytes per tile,
- burst length class,
- read/write phase,
- buffer capacity,
- overlap with compute,
- bandwidth safety margin,
- latency-hiding requirement.

For M0, the key equation class is:

#+begin_src text
time_fetch_tile <= time_compute_tile + allowed_stall
#+end_src

or equivalently:

#+begin_src text
ddr_bytes_per_tile / effective_ddr_bandwidth <= compute_cycles_per_tile / clock
#+end_src

This is not exact DDR controller modeling. It is a feasibility guard that
prevents OR-Tools from proposing compute parallelism that the memory system
cannot feed.

** PCIe

PCIe should initially be outside the inner inference loop.

For OR-Tools, model PCIe first as phase-level orchestration:

- weight load/setup cost,
- input prompt transfer,
- output token/result transfer,
- command/control latency,
- experiment/HIL overhead.

Do not make PCIe a per-tile hot-path constraint in M0 unless the architecture
explicitly streams weights or activations from the host during inference. The
first YPCB monkey is DDR3-resident inference, not host-streamed inference.

* YPCB-specific interpretation

YPCB constraints from the current board profile:

- Kintex-7 class fabric,
- no URAM,
- finite BRAM,
- DDR3 external memory,
- PCIe host interface,
- open-source build target via yosys/nextpnr-xilinx.

Consequences:

- weight storage will quickly exceed BRAM for useful models,
- DDR3 scheduling is not optional,
- accumulator and tiling choices must account for BRAM pressure,
- high-end HBM assumptions from U280/U55C papers do not transfer directly,
- proprietary-HLS papers can inform architecture, but not direct workflow.

* Monkey / pedestal split

** Monkeys

1. DDR3-aware OR-Tools scheduling:
   - can the solver choose tile/buffer/parallelism values that respect measured
     DDR3 bandwidth and still give useful compute utilization?

2. Parameterized hardware family:
   - can one generated/template Linear family realize many solver candidates
     without manual RTL redesign?

3. EDA feedback learning:
   - do yosys/nextpnr failures cluster in ways OR-Tools can use as constraints,
     margins, or ranking penalties?

4. Model-to-solver semantics:
   - later, can PyTorch/ONNX shapes and quantization policies be extracted
     reliably enough for the solver?

** Pedestals

- JSON schemas,
- report generation,
- CLI wrappers,
- pretty dashboards,
- general model import,
- full experiment DB,
- polished candidate registry.

Pedestals are useful only when they support the monkeys above.

* Ladder from zero to TinyStories-1M

** L0: DDR3 bandwidth characterization

Goal:
- measure or conservatively estimate sustainable DDR3 bandwidth for YPCB.

Output:
- board-profile update with effective bandwidth and safety margin.

Monkey tested:
- whether the memory envelope is credible enough for solver constraints.

** L1: synthetic memory-bound Linear

Goal:
- weights are DDR3-resident,
- activations and partial sums are on-chip,
- OR-Tools chooses tile size, lanes, buffer depth, burst class, and prefetch
  distance.

Output:
- first M0 candidate set and estimated no-stall/stall schedule.

Monkey tested:
- DDR3-aware architecture scheduling.

** L2: parameterized quantized Linear kernel

Goal:
- one hardware/template family supports the candidate choices from L1.

Output:
- generated/buildable RTL or equivalent template configs for multiple
  candidates.

Monkey tested:
- whether solver choices map to implementable hardware without manual redesign.

** L3: yosys/nextpnr feedback loop

Goal:
- synthesize/route selected candidates,
- classify failures,
- add no-goods or safety margins.

Output:
- CP batch 1 improves over CP batch 0 or the approach is narrowed/killed.

Monkey tested:
- whether EDA reality becomes solver knowledge.

** L4: TinyStories-like Linear dimensions

Goal:
- replace synthetic dimensions with real TinyStories-1M layer shapes.

Output:
- same solver/hardware loop works for real model-derived Linear layers.

Monkey tested:
- whether the synthetic memory-bound result transfers.

** L5: FFN block

Goal:
- compose two Linear layers plus activation,
- choose intermediate buffering and fusion/split schedule.

Output:
- first multi-operator solver plan.

Monkey tested:
- operator composition and buffer reuse.

** L6: TinyStories-1M graph

Goal:
- import PyTorch/ONNX graph,
- map supported operators,
- leave unsupported operators on host or stub them explicitly.

Output:
- board-aware architecture plan for a tiny model, with honest unsupported-op
  boundaries.

Monkey tested:
- model-to-solver semantics.

* State-of-art gap

The strongest defensible gap statement is:

#+begin_quote
Prior work shows CP/SAT can optimize HLS scheduling, resource binding,
communication scheduling, and restricted physical-design subproblems. Prior LLM
FPGA work shows many quantized and memory-aware accelerator architectures. What
appears underdeveloped is a practical open-toolchain loop where CP-SAT performs
DDR3-aware inverse architecture scheduling for LLM operators on a constrained
Kintex-7 board, then learns from yosys/nextpnr feedback.
#+end_quote

This is a good moonshot wedge because it is narrow, testable, and exposes the
actual risk before building a full PyTorch/ONNX-to-FPGA stack.
